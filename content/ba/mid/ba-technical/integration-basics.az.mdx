## Öyrənmə məqsədləri

- DB commit ilə message publish-in niyə fərqlənə bildiyini izah et.
- Aydın transaction sərhədində outbox publishing və consumer deduplication qur.
- Webhook üçün signature verification, replay handling və reconciliation müəyyən et.

## Bu mövzu niyə vacibdir

Commerce xidməti order-i commit edib OrderCreated publish etməmiş crash edir. Customer order nömrəsi görür, warehouse event almır. Əks sıra da risklidir: əvvəl publish DB transaction sonra rollback olanda shipment başlada bilər. Dizayn iki müstəqil sistemin birlikdə commit etdiyini fərz etmək əvəzinə boşluğu qarşılamalıdır.

## Əsas anlayışlar

Synchronous request caller time budget daxilində response gözləyir. Async iş acceptance-ı eventual completion-dan ayırır. Queue işi buferləyir, event baş verəni təsvir edir. Fərq payload-un JSON olmasında deyil, məsuliyyət və zamandadır.

Transactional outbox business record və event record-u eyni local DB transaction-da yazır. Ayrı publisher committed event-i broker-ə göndərib sonra publication-u qeydə alır. Göndərdikdən sonra success yazmamış crash etsə təkrar göndərə bilər. Pattern commit/publish boşluğunu önləyir, duplicate delivery-ni tam silmir.

Consumer sabit event ID ilə business effect-i eyni local transaction-da yaza bilər. ID artıq tətbiq edilibsə effect-i təkrarlamadan ack et. İlkin SELECT və əlaqəsiz INSERT concurrency zəmanəti deyil. DB uniqueness/transaction mexanizmi istifadə et. Retention gözlənilən redelivery/reconciliation müddətini əhatə etsin.

Ordering ayrıca contract-dır. Event daha yenisindən sonra gələ bilər. Entity üzrə sequence/version seç, gap-i defer, reject və ya reconcile etməyi müəyyən et. Ayrı maşın timestamp-lərindən qlobal order çıxarma.

Webhook HTTP callback-dir. Parsed content-ə güvənməzdən əvvəl provider signature-ını dəqiq ilkin body byte-larında yoxla. GitHub nümunəsi HMAC-SHA256 və X-Hub-Signature-256 istifadə edir; başqa provider fərqli header/algorithm seçir. Valid signature qorunan byte-ları authenticate edir; özü freshness, uniqueness, hər business effect üçün permission və eventual delivery sübut etmir.

## İşlənmiş nümunə

Orders service O-81 order-i və E-81 outbox event-i bir relational transaction-da saxlayır. İlk ack itirildiyi üçün worker E-81-i iki dəfə göndərir. Warehouse consumer processed-event record-da unique key-i stock reserve edən transaction-la birlikdə istifadə edir. Yalnız bir reservation commit olunur.

```sql
BEGIN;
INSERT INTO processed_events (consumer_name, event_id)
VALUES ('warehouse-reservation', 'E-81');
-- A uniqueness conflict means this consumer already applied the event.
UPDATE inventory SET reserved = reserved + 1
WHERE sku = 'COURSE-1' AND available - reserved >= 1;
-- Check the affected-row count; a failed reservation needs a business outcome.
COMMIT;
```

Bu, tam DB implementasiyası deyil, transaction boundary pseudocode-udur. Uniqueness conflict seçilmiş DB transaction mexanizmi ilə idarə edilməlidir. Stock shortage sonsuz retry yox, explicit status və ya compensation workflow istəyən business rejection-dır.

## Qərarı təhlil et

<details>
<summary>Provider webhook-u düzgün imzalayıb. Event ID izləməsini keçmək olarmı?</summary>

Xeyr. Həqiqi delivery retry ola bilər; freshness control yoxdursa köhnə signed body replay edilə bilər. Signature-ı yoxla, provider timestamp policy verirsə tətbiq et; authenticated event identifier və durable record ilə deduplicate et.

</details>

## Tipik səhvlər

- Scope göstərmədən “exactly once” demək transport delivery-ni bir committed business effect-lə qarışdırır.
- Durable acceptance-dan əvvəl webhook ack etmək crash-də event itirə bilər.
- Verification-dan əvvəl JSON re-serialize etmək byte-ı dəyişib qanuni signature-ı poza bilər.
- Shared signing secret-i log-a yazmaq onunla gələn bütün future delivery-ni ifşa edir.
- Əlaqəsiz Cosmos DB partition-larında outbox qurmaq mənbənin vermədiyi atomic boundary-ni fərz edir.

## Praktik tapşırıq

Provider payment-confirmed webhook-u 72 saat redeliver edə bilər. Handler JSON parse edir, loyalty point əlavə edib 200 verir. Parallel duplicate, storage outage, old event və provider-specific signing key rotation daxil əvəzedici flow yaz.

## Nümunə həll

<details>
<summary>Nümunə həlli göstər</summary>

Body size həddi ilə raw byte oxu, qorunan active key ilə provider signing qaydasını yoxla, sənədləşmiş signed timestamp tolerance tətbiq et. Event schema validate et, expected merchant/account-a bağla. Bir local transaction-da provider/event ID yaz, point-i həmin event üçün bir dəfə tətbiq et. Parallel duplicate üçün uniqueness constraint istifadə et. Tanınmış duplicate point təkrarlamadan success ack ala bilər.

Durable acceptance fail olarsa success iddiası deyil, documented retryable failure qaytar. Deduplication record-u ən az delivery/reconciliation policy müddətincə saxla; 72 saatdan uzun ola bilər. Planned key rotation-da yalnız configured provider overlap key-lərini müəyyən transition window-da qəbul et. Sübut natamamdırsa payment state-ni provider-lə reconcile et.

</details>

## Bilik yoxlaması və yaddaş vərəqi

Business record + outbox birlikdə commit. Retry ilə publish. Deduplicate + effect birlikdə. Raw byte yoxla. Signature validity replay protection deyil. Async işi complete saymamış ordering, dead-letter handling və reconciliation qur.
