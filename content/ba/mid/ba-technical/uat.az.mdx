## Öyrənmə məqsədləri

- Acceptance testing-i technical check və sign-off-dan ayır.
- Biznes meyarından normal, boundary və exception case qur.
- Result, unresolved issue və release authority-ni yaz.

## Bu mövzu niyə vacibdir

API unit test-dən keçir, amma işçilər gün sonunda refund-u reconcile edə bilmir. User Acceptance Testing həllin təmsilçi şəraitdə agreed business use-u dəstəkləməsini yoxlayır. Technical testing-i tamamlayır; sübutlar ayrı suallara cavab verir.

## Əsas anlayışlar

Business need və requirement version-a bağlı acceptance criteria-dan başla. Mənalı execution üçün user/nümayəndə, environment, data, access, business rule və dependency müəyyən et. Development team demo-su acceptance-a kömək edə bilər; user-in işi özü görməsinə avtomatik bərabər deyil.

Test case precondition, data, action və expected observable result verir. Uyğun yerdə success, invalid input, boundary, authorization, exception və recovery daxil et. Expected result pass-ı inandırıcı izahdan ayıracaq qədər konkret olsun. Yaşıl status üçün sistemi gördükdən sonra expected result dəyişmə.

Uyğun synthetic/approved data istifadə et. Kritik external dependency-ni keçən environment tam production journey-ni sübut etmir; limiti göstər, ayrıca sübut al. Yalnız admin happy path-i deyil, role permission və accessibility ehtiyacını yoxla.

Actual result, evidence reference, defect və retest status saxla. Severity təsiri, priority nə vaxt hərəkəti göstərir; təşkilat öz scale-ını seçə bilər. Biznes nümayəndəsi ciddi issue tapa bilər, amma təkbaşına release authority-si olmaya bilər. Release qərarı open defect, risk acceptance, operational readiness və rollback/recovery limit-ini nəzərə almalıdır.

Acceptance criteria, verification, validation və approval ayrıdır. Test yazılmış criteria-nı ödəyib vacib need-in buraxıldığını göstərə bilər. Boşluğu eskalasiya et, controlled information-u agreed proseslə yenilə. İmzanı bütün behavior-un icra sübutu sayma.

## İşlənmiş nümunə

Refund UAT case settled 100 vahid payment və icazəli operator ilə başlayır. 40 vahid partial refund istə, provider outcome-u təsdiqlə; remaining refundable amount 60 olsun. Eyni operation identifier-i təkrarla, əlavə refund olmasın. Yeni 70 request stated policy-yə görə rədd edilsin.

Timeout case görünən unresolved status və reconciliation path gözləyir. Environment həmişə mock success verirsə timeout davranışını sübut etmir. Limiti yaz, tam acceptance coverage iddiasından əvvəl missing path üçün controlled evidence təşkil et.

## Qərarı təhlil et

<details>
<summary>User demo-dan sonra screen-i approve edir. Bütün exception path-lər UAT-dan keçibmi?</summary>

Xeyr. Müşahidə yalnız həmin şəraitdə göstərilən behavior-u dəstəkləyir. Planned case, actual execution və untested path-i tap. Stakeholder feedback-ini cavabdehi olan acceptance/release qərarından ayır.

</details>

## Tipik səhvlər

- Yalnız admin permission ilə test etmək.
- Expected result kimi “düzgün işləyir” yazmaq.
- Mock və çatışmayan integration-u gizlətmək.
- Bütün open defect-i ya avtomatik blocker, ya avtomatik məqbul saymaq.

## Praktik tapşırıq

Booking cancellation üçün üç UAT case yaz: uğurlu cancellation, unauthorized caller, unknown payment provider outcome. Hər biri üçün sübut və sahib göstər.

## Nümunə həll

<details>
<summary>Nümunə həlli göstər</summary>

Booking state, caller role və payment precondition müəyyən et. Success agreed final state/customer message verməlidir; unauthorized caller booking-i dəyişməməli, protected data almamalıdır. Unknown provider outcome reconciliation sahibi ilə açıq pending qalmalıdır. Request identifier, redacted response və resulting state saxla; unresolved risk-i səlahiyyətli qərarverən qiymətləndirsin.

</details>

## Bilik yoxlaması və yaddaş vərəqi

Criterion + precondition + action + observable result + evidence + cavabdehi olan qərar. Technical pass, user observation və release approval ayrı qeyddir.
