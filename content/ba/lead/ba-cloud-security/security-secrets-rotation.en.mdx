## Learning objectives

- Distinguish secret storage, encryption and authorization.
- Plan rotation according to credential or key type.
- Respond to exposure without assuming deletion removes compromise.

## Why this matters

A token accidentally committed to Git may remain usable after the file is deleted. A signing-key rotation can break legitimate verification if old public keys disappear too early, while an encryption-key deletion can make retained data unreadable. Lifecycle decisions need the type of secret and its dependencies.

## Core theory

Inventory secrets and keys with purpose, owner, consumers, scope, storage, lifetime and recovery requirements. API credentials, signing keys, encryption keys and user passwords do not share one interchangeable handling model. User passwords normally require suitable password hashing; reversible service credentials need a different protected storage contract.

Use appropriate secret-management and workload-identity mechanisms rather than embedding values in code, images, logs or exported test environments. Storage encryption protects one boundary but does not make broad read access acceptable. Authorize secret retrieval narrowly and audit relevant access without recording the secret value itself.

Rotation introduces new credential material and moves consumers safely. Determine propagation, overlap, cache lifetimes, rollback and verification. Prefer short-lived workload credentials where supported, but remember that their issuance policy still needs least privilege. A rotation job succeeding is not proof that every consumer stopped using the old credential.

Revocation removes authority under the relevant system's model. Deleting a repository file or rotating one password does not necessarily revoke other derived tokens, sessions or copied credentials. During exposure, identify the affected authority, revoke or contain it, inspect access evidence and restore a controlled state.

For signing keys, publish and trust new verification material through the configured issuer process and consider legitimate token lifetimes and caches. A compromised key can require emergency rejection rather than a normal overlap window. For encryption keys, preserve the ability to decrypt retained data or perform controlled re-encryption before retirement; losing a key can mean losing the data.

Test recovery and break-glass paths under controlled access. Audit who authorized emergency use and how temporary privileges are removed. Avoid scattering raw secret values through incident notes, screenshots or exception traces while trying to investigate the exposure.

## Worked example

A service credential has two known consumers. The owner issues a new scoped credential, updates the secret store, rolls consumers deliberately and verifies successful requests under the new identity. Metrics and safe audit identifiers show that the old credential is no longer used before normal revocation.

If the old credential was publicly exposed, the team instead contains or revokes the compromised authority promptly according to incident risk, then restores service under a controlled replacement. It does not wait for the ordinary overlap schedule merely for convenience. No real credentials or key material are created in this lesson.

## Inspect the decision

<details>
<summary>A leaked credential is removed from the latest commit. Is the incident resolved?</summary>

No. Copies and repository history can retain it, and the authority may still be valid. Revoke or contain the credential through its issuing system, investigate relevant use and replace consumers safely. Cleaning source history alone is not credential revocation.

</details>

## Common mistakes

- Using the same rotation procedure for passwords, signing and encryption keys.
- Printing secret values to prove a deployment updated.
- Retiring decryption keys before retained data is handled.
- Assuming a short lifetime removes the need for a scoped trust policy.

## Practice exercise

Plan rotation for an API credential used by a scheduled job and a web service. Include consumer discovery, rollout verification, old-credential retirement and an emergency exposure path.

## Worked solution

<details>
<summary>Show worked solution</summary>

Identify both consumers and their schedules, issue a minimally scoped replacement and deliver it through controlled storage. Verify each consumer uses the new authority with non-secret identifiers, including the next scheduled run. Retire the old credential under the defined overlap and recovery policy. For exposure, contain or revoke promptly based on risk, inspect access and restore controlled service rather than following an unexamined normal schedule.

</details>

## Check understanding and cheat sheet

Know the secret type and consumers. Store and authorize separately. Rotate with evidence. Revoke compromised authority. Retire encryption keys only with retained-data and recovery requirements addressed.
