## Əsas anlayış

Requirements Analysis and Design Definition finding-i istifadə edilən representation-a çevirir, keyfiyyət/uyğunluğunu yoxlayır, əlaqələri təşkil edir, value yollarını müqayisə edir. BABOK v3-də requirement need-i, design solution-u təmsil edir. Əlaqə iterativdir: design əlavə requirement aça bilər. Analiz software ilə yanaşı process, people, information və rule-a aiddir. Faydalı tövsiyə geniş scope-u saxlayır.

## Niyə vacibdir

Mükəmməl formatlı requirement yanlış capability təsvir edə bilər. Ayrılıqda faydalı requirement-lər birlikdə conflict yarada bilər. Məsələn, dərhal deletion və uzun audit retention scope/şərt birlikdə baxılanadək uyğun görünə bilər. Verification, validation və requirements architecture bu problemlərə ayrı sual verir. Hamısını eyni “review” saymaq hər item-də reference/imza olsa da kritik boşluq qoyar.

## Nəzəriyyə və fərqlər

**Specify/model:** auditoriya/purpose-a uyğun text, matrix, diagram seç. Modeling müxtəlif vəziyyətdəki elicitation result-dan başlaya və əlavə elicitation aça bilər. **Verify:** representation-un quality tələbinə, sonrakı istifadəyə uyğunluğunu yoxla. Ambiguity, uyğunsuz term, missing detail, infeasibility və test edilməyən statement axtar. Quality tək template uyğunluğu deyil, intended use-a yararlılıqdır.

**Validate:** requirement/design-ın business requirement-ə uyğunluğunu və lazım olan value-nu dəstəkləməsini yoxla. Benefit assumption, evaluation criteria, scope alignment aç. Validation verification bitməmiş başlaya bilər, amma verification tamamlanmamış tamamlana bilməz. **Approval** səlahiyyətli razılaşma barədə ayrıca governance qərarıdır.

**Requirements architecture:** requirement-lər objective üçün birgə işləsin deyə view/model təşkil et. Traceability relation göstərə bilər; tək link bütövlüyü sübut etmir. **Design option:** yaratmaq, almaq və birləşdirmək; integration, requirement-in component/release üzrə bölgüsünü düşün. **Potential value:** benefit, cost, risk, dependency, resource constraint müqayisə et. Maintenance, intangible effect və seçilməyən ən yaxşı alternativin opportunity cost-unu daxil et. Estimate qeyri-müəyyəndir. Bəzən əlavə investigation, bir neçə proof of concept və ya heç nə etməmək ən əsaslı tövsiyədir.

## İşlənmiş nümunə

Benefits agentliyinə etibarlı case handling və şəxsi record-a uyğun access lazımdır. Bir requirement “case bağlananda record sil”, digəri “authorized reviewer closed case-i görə bilsin” deyir. Traceability matrix hər ikisini objective-ə bağlayır, amma uyğun şərti sübut etmir.

Analyst hər statement üçün record, user, event və retention constraint-i aydınlaşdırır. State model/role view conflict-i açır. Variant mövcud service configuration, component purchase və combined development-dir. Müqayisə integration, operational effort, access control, uncertainty və desired outcome-u nəzərə alır. Legal retention müddəti uydurulmur; qayda səlahiyyətli mənbədən gəlməlidir.

Diaqram üç check-i option comparison-dan ayırır. Oxlar məcburi birdəfəlik sıra deyil, information dependency göstərir. Hər yoxlama gap aşkar edəndə rework ola bilər.

## Qərar məşqi

Specification quality checklist-dən keçir; sponsor value-nun sübutunu soruşur. Real nəticəni izah et: representation sonrakı iş üçün yararlı ola bilər. Yenə business need alignment və inandırıcı benefit gözləntisi lazımdır. Müsbət potential value estimate real istifadə value-sunu sübut etmir. Verified statement, validated requirement, approved decision və sonrakı solution evaluation fərqini saxla.

## Tipik səhvlər və yaxşı təcrübə

- Düzgün notation-u düzgün business outcome sayma.
- Verification natamamkən validation-u complete adlandırma.
- Reference link requirement-lərin işlək bütöv olması sübutu deyil.
- Integration, maintenance, stakeholder effect-i buraxıb yalnız purchase price müqayisə etmə.
- Uncertain benefit-i guaranteed return etmə.
- Qərar səlahiyyətini analyst-in tövsiyə hazırlama məsuliyyətindən ayır.

## Tətbiq tapşırığı və izahlı cavab

**Tapşırıq:** “service sürətli olmalıdır” və əlaqəsiz report üçün aydın requirement-i qiymətləndir. Closed-case nümunəsinə bir architecture sualı, option comparison-da tez-tez unudulan bir cost seç.

**İzahlı cavab:** “sürətli” intended purpose üçün yararlı tərif deyil; verification ambiguity və uyğun measure ehtiyacını açmalıdır. Dəqiq, amma əlaqəsiz report need/scope-u dəstəkləmədiyi üçün validation-dan keçməyə bilər. Architecture sualı deletion, access, case state və record type-ın ziddiyyətsiz birgə işləməsidir. Davamlı integration support və deferred alternative-in value-su müqayisəni dəyişə bilər. Güclü cavab hər problemin ayrı check-ə aidliyini izah edir.

## Mini-test

Dərhal problemin representation quality, value alignment, coherent relation, option definition və ya recommendation olduğunu tap. Bir neçə problem ola bilər, amma ən yaxşı növbəti addım ssenaridəki evidence gap-i qarşılamalıdır.

## Yaddaş vərəqi

Verification: istifadəyə yararlı information. Validation: need/value uyğunluğu. Architecture: requirement-lərin bütöv işləməsi. Option: onları ödəyən alternativ. Recommendation: uncertain potential value/nəticə müqayisəsi. Approval və actual value evaluation ayrıdır.
